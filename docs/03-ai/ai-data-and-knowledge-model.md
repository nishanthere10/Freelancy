## 1. Overview

The Freelance OS AI platform operates over three categories of knowledge. Each category has a different storage mechanism, access pattern, and authority level.

```
Knowledge Category         Storage                  Authority
─────────────────────────────────────────────────────────────
Structured Knowledge   →   Neon PostgreSQL        →  Highest (source of truth)
Activity Knowledge     →   activity_events table  →  High (verified historical record)
Semantic Knowledge     →   Chroma vector store    →  Medium (retrieval index, not authority)
```

The LLM inference output is the **lowest** authority. It is reasoning over the above knowledge — not a source of facts.

## 2. Structured Knowledge

### 2.1 Definition

Structured knowledge is the authoritative business data stored in Neon PostgreSQL. It is managed by the existing domain services and is the ground truth for all financial and operational facts.

### 2.2 Existing Tables (Relevant to AI)

From `packages/database/src/` (Drizzle ORM schemas):

| Table | AI-Relevant Fields |
|-------|--------------------|
| `users` | `id`, `clerkId`, `email`, `name` |
| `workspaces` | `id`, `name`, `slug`, `ownerId` |
| `workspace_members` | `workspaceId`, `userId`, `role` |
| `clients` | `id`, `workspaceId`, `name`, `email`, `phone`, `company` |
| `projects` | `id`, `workspaceId`, `clientId`, `name`, `status`, `budget`, `startDate`, `endDate`, `description` |
| `invoices` | `id`, `workspaceId`, `clientId`, `projectId`, `number`, `status`, `total`, `dueDate` |
| `invoice_items` | `invoiceId`, `description`, `quantity`, `unitPrice`, `amount` |
| `invoice_history` | `invoiceId`, `status`, `changedAt` |
| `activity_events` | `id`, `workspaceId`, `entityType`, `entityId`, `actorUserId`, `eventType`, `metadata`, `createdAt` |

### 2.3 AI Access Pattern

- AI reads structured knowledge through typed, workspace-scoped tool functions.
- AI never writes to structured knowledge directly.
- Mutations triggered by AI recommendations flow through the existing domain services (human review → user confirms → domain service executes).

### 2.4 Authority

When PostgreSQL returns a fact, it is the ground truth:

```
PostgreSQL: invoice total = ₹32,000
→ AI context must reflect ₹32,000
→ No other source can override this fact
→ LLM must not produce a different number
```

## 3. Activity Knowledge

### 3.1 Definition

Activity knowledge is the temporal business event log stored in the `activity_events` table (built in Sprint 10). It captures the sequence of events that shaped the current state of the business.

### 3.2 What Activity Captures

The existing Activity domain captures domain events for all core entities:

| Domain | Events |
|--------|--------|
| Workspace | `workspace.created`, `workspace.deleted`, `workspace.restored`, `workspace.member_added`, `workspace.member_removed`, `workspace.member_role_changed`, `workspace.ownership_transferred` |
| Client | `client.created`, `client.updated`, `client.deleted`, `client.restored` |
| Project | `project.created`, `project.updated`, `project.deleted`, `project.status_changed`, `project.restored` |
| Invoice | `invoice.created`, `invoice.sent`, `invoice.payment_recorded`, `invoice.cancelled` |

Each event includes: `actorUserId`, `entityType`, `entityId`, `workspaceId`, `eventType`, `metadata` (payload), `createdAt`.

### 3.3 Why Activity Is Valuable for AI

Activity is the **narrative of the business**. It answers questions that structured data cannot:

- "What changed and when?"
- "Who made the last change?"
- "What was the sequence of events leading to this overdue invoice?"
- "When did this project's status change to on_hold?"

Structured data shows the current state. Activity shows the history of how the state was reached.

### 3.4 AI Access Pattern

- AI queries activity via the existing activity retrieval infrastructure.
- Queries are always scoped to `workspaceId` and optionally filtered by `entityType`, `entityId`, time range, and event type.
- Activity results are labeled as historical evidence (second priority, below SQL facts).

## 4. Semantic Knowledge

### 4.1 Definition

Semantic knowledge is unstructured or semi-structured content indexed in Chroma for fuzzy, semantic retrieval. It answers questions that require reading documents, not querying rows.

### 4.2 Document Types

| Document Type | Content | Created By |
|---------------|---------|-----------|
| Scope documents | Structured scope generated by AI Scope Analysis | AI + user confirmation |
| Proposals | Pricing, timeline, deliverables for client | User-authored or AI-drafted |
| Meeting notes | Discussion records from client meetings | User-authored |
| Retrospectives | Lessons learned after project close | User-authored |
| Client notes | Communication preferences, behavioral observations | User-authored |
| Contracts / briefs | Formal agreements or client briefs | User-uploaded |

Initial focus: **scope documents** generated by the Scope Analysis feature. Other document types are planned but require a document capture UI (future work).

### 4.3 Semantic Knowledge Is NOT Authoritative

A document saying "the project budget is ₹2 lakh" is informational — it reflects what was written in the proposal. The authoritative budget is the `budget` field in the `projects` table. If they conflict, PostgreSQL wins.

## 5. Document Model

### 5.1 Document Entity

A document is the unit of semantic knowledge before chunking.

```typescript
interface Document {
  documentId: string;          // UUID
  workspaceId: string;         // UUID — tenant isolation
  entityType: string;          // 'project' | 'client' | 'invoice' | 'general'
  entityId: string;            // UUID of related entity
  sourceType: string;          // 'scope_document' | 'proposal' | 'meeting_note' | 'retrospective' | 'client_note' | 'contract'
  title: string;               // Human-readable title
  content: string;             // Full text content
  documentVersion: number;     // Monotonically increasing version
  authorUserId: string;        // UUID of the user who created/uploaded
  createdAt: string;           // ISO 8601
  updatedAt: string;           // ISO 8601
}
```

### 5.2 Chunk Entity

A chunk is the unit indexed in Chroma.

```typescript
interface DocumentChunk {
  chunkId: string;             // UUID — deterministic: documentId + version + index
  documentId: string;          // Parent document
  documentVersion: number;     // Version of the parent document
  workspaceId: string;         // Tenant isolation
  entityType: string;
  entityId: string;
  sourceType: string;
  chunkIndex: number;          // Position within the document
  content: string;             // Chunk text
  embedding: number[];         // Jina embedding vector
  createdAt: string;
}
```

### 5.3 Why Chunks Carry Document Metadata

Each chunk must be self-contained enough to be cited independently. When a retrieved chunk is shown to the user as evidence ("The original scope said..."), the user needs to know which document, which version, and which entity it came from — without fetching the parent document.

## 6. Embedding Model

```
Document chunk text
      ↓
Jina Embedding Provider
      ↓
float[] (embedding vector)
      ↓
Stored in Chroma with chunk metadata
```

The embedding transforms text into a position in a high-dimensional semantic space. Documents with similar meaning are positioned near each other.

**Model configuration (to be evaluated):**

```typescript
const JINA_EMBEDDING_MODEL = "jina-embeddings-v3"; // Example — verify current availability
const JINA_EMBEDDING_DIMENSIONS = 1024;            // Depends on model selection
```

These constants must be verified against Jina's current API offerings before implementation. The vector dimension must match the Chroma collection configuration.

## 7. Knowledge Gaps and Completeness

The AI platform can only reason over data that exists in the system. Current gaps:

| Gap | Impact | Resolution |
|----|--------|-----------|
| No scope documents exist yet | Scope Analysis cannot retrieve historical scopes until users generate them | Scope Analysis (Phase 1) generates them |
| No retrospectives exist yet | Client Intelligence cannot draw on lessons learned | Retrospective UI required (future work) |
| No meeting notes | Cannot answer questions about client discussions | Document capture UI required (future work) |
| No proposals stored as documents | Cannot compare current ask against original proposal | Proposal document storage required (future work) |

The AI system degrades gracefully when knowledge is sparse — it returns results based on available evidence and flags insufficient context explicitly.

## 8. Memory Model

Memory is the AI's ability to recall context across interactions. It has two distinct types that must not be mixed.

### 8.1 Business Knowledge (Persistent)

Business knowledge is the structured, activity, and semantic knowledge described in Sections 2–4. It is:

- Owned by the workspace.
- Durable (persists indefinitely until explicitly deleted).
- Versioned (scope documents have versions).
- Scoped to the workspace (never cross-tenant).
- Authority-ranked (PostgreSQL > Activity > Semantic).

### 8.2 Conversation Memory (Transient)

Conversation memory is the context of a specific AI interaction — what the user asked, what the AI said, and the current workflow state.

```typescript
interface ConversationContext {
  sessionId: string;
  workspaceId: string;
  actorUserId: string;
  workflowType: string;
  messages: Array<{ role: 'user' | 'assistant'; content: string; timestamp: string }>;
  workflowState: Record<string, unknown>;   // LangGraph state snapshot
  createdAt: string;
  expiresAt: string;                        // Conversation memory expires
}
```

Conversation memory is transient. It:

- Scoped to a single user session / workflow run.
- Not persisted beyond the session by default.
- Subject to expiration / retention policy.
- Does not leak across users within a workspace.

### 8.3 Long-Term Memory (Future)

Future versions may implement persistent, workspace-scoped memory for recurring patterns:

- Workspace-level memory (preferred models, documentation style).
- Client-level memory (known behavioral patterns).
- Project-level memory (past decisions and constraints).

Long-term memory requires explicit design for:

- **Scope:** What can be remembered and at what level.
- **Ownership:** Which workspace/user owns each memory.
- **Expiration / retention:** How long memories are kept.
- **Provenance:** Where the memory came from (conversation, user action).
- **Security:** No cross-workspace memory leakage.
- **Deletion:** Ability to remove specific memories on user request.

Long-term memory is explicitly deferred from the initial implementation.

## 9. Source Provenance

Every piece of information in the AI context must be traceable to its origin:

| Source | Provenance Data |
|--------|----------------|
| SQL fact | Table + column + query filter + timestamp |
| Activity event | `activity_events.id` + `eventType` + `createdAt` + `actorUserId` |
| Document chunk | `documentId` + `documentVersion` + `chunkId` + `sourceType` + `entityId` |
| LLM inference | Model identifier + prompt version + timestamp |

Provenance is used for:
- Grounded citations in responses.
- Debugging incorrect AI answers.
- Security audits.
- Identifying stale or conflicting information.

## 10. Document Lifecycle

### Creation

```
User creates / confirms scope document (or uploads document)
      ↓
Document stored (initial version = 1)
      ↓
Ingestion pipeline triggered
      ↓
Chunks indexed in Chroma
```

### Update

```
User updates document
      ↓
documentVersion incremented
      ↓
Old chunks for this documentId deleted from Chroma
      ↓
New chunks created, embedded, upserted
```

### Deletion

```
User deletes document (or entity is deleted)
      ↓
Document marked as deleted / archived
      ↓
All chunks for this documentId removed from Chroma
```

The vector index must stay synchronized with the document lifecycle. Stale vectors from deleted or updated documents are a retrieval quality problem and a potential data integrity issue.

---

## 11. Workspace Scoping

Every piece of knowledge is workspace-scoped. This is enforced at every layer:

| Layer | Enforcement |
|-------|------------|
| Structured knowledge | Drizzle ORM queries always include `WHERE workspace_id = ?` |
| Activity knowledge | Activity retriever always filters by `workspaceId` |
| Semantic knowledge | Chroma queries always include `workspaceId` metadata filter |
| LLM context | Context Builder never combines results from different workspaces |
| AI tools | All tools require `workspaceId` as a required parameter |

There is no path through the AI system that allows cross-workspace knowledge retrieval.

---

## 12. Data Retention and Deletion

Retention policies must be defined before any AI data is persisted:

| Data Type | Default Retention | Deletion Trigger |
|-----------|-----------------|-----------------|
| Structured knowledge (PostgreSQL) | Follows existing domain lifecycle | User deletes entity |
| Activity events | Indefinite (existing behavior) | No auto-deletion currently |
| Document chunks (Chroma) | Synchronized with document lifecycle | Document deleted or workspace deleted |
| Conversation memory | Short-term (session-based) | Session ends or expires |
| LangSmith traces | Per LangSmith configuration | Per LangSmith retention settings |

AI provider data retention (Groq, Jina, Chroma) must be reviewed before production data is sent to those services. See [`ai-security-and-governance.md`](./ai-security-and-governance.md) for provider trust evaluation.

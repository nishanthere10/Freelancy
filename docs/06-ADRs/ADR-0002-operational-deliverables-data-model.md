# ADR-0002: Normalization of Operational Project Deliverables into First-Class Database Entities

**Status:** APPROVED  
**Date:** September 13, 2026  
**Deciders:** Principal Architect & Lead Full-Stack Engineer  
**Sprint Context:** Sprint 17 — Project Hub & Deliverables Execution Engine  

---

## 1. Context & Problem Statement

In Sprint 16, Freelance OS enabled converting confirmed AI scopes into live projects (`projects` table) and optional deposit invoices (`invoices` table). However, the resulting deliverables generated by the LLM and edited by the freelancer remained stored exclusively inside `scope_analyses.result` (a JSONB column).

When viewing a project in `ProjectDetail.tsx`, the application cannot track active execution because:
1. Deliverables lack independent mutable state (status, logged hours, completion dates).
2. The project detail page cannot update or query individual milestone progress without mutating the original scope JSON.
3. Invoices, activity logs, and future change orders cannot establish referential integrity to individual deliverables.

We must decide whether to keep deliverables in JSONB and project an execution layer over it (Option A) or normalize deliverables into dedicated relational entities (Option B).

---

## 2. Options Considered

### Option A: Retain Deliverables in JSON (`scope_analyses.result` or `projects.execution_state` JSONB)
- **Mechanism:** Maintain deliverables as JSON arrays inside `scope_analyses.result` or add a new `projects.execution_state` JSONB column.
- **Cons:**
  - **Mutating Contractual Baseline:** Mutating `scope_analyses.result` violates the core system invariant that a confirmed scope is an immutable historical baseline used for Scope Drift detection.
  - **No Referential Integrity:** Future change orders, invoice line items, and audit logs cannot maintain foreign keys to specific deliverables.
  - **Concurrency & Partial Updates:** Updating a single deliverable status or logged hours requires read-modify-write on the entire JSON object, risking lost updates under concurrent interactions.
  - **Poor Queryability:** Filtering deliverables by status across a workspace or computing aggregated team progress in SQL requires slow, complex JSON path expressions.

### Option B: Normalize Deliverables into a Dedicated `project_deliverables` Table (APPROVED)
- **Mechanism:** Introduce a first-class `project_deliverables` table linked to `projects(workspace_id, id)` with composite foreign keys and tenant isolation.
- **Pros:**
  - **Stable Operational Identity:** Once an AI deliverable becomes an active project deliverable, it has a stable UUID, distinct lifecycle states (`pending`, `in_progress`, `completed`), and deterministic ordering.
  - **Clean Architectural Separation:** The confirmed scope (`scope_analyses`) remains immutable as the planning baseline. The operational deliverables (`project_deliverables`) represent live execution state. Provenance is maintained via `source_scope_id`.
  - **Strict Relational Integrity:** Enforces workspace tenant isolation using composite foreign keys `(workspace_id, project_id)`.
  - **Billing & Concurrency Tracking:** First-class fields `billed_at` and `invoice_id` track progress invoicing cleanly, enabling atomic conditional updates that prevent duplicate billing races.
  - **Deterministic Progress Calculations:** Simple, indexed SQL / domain service aggregation for completed counts, logged vs estimated hours, and completion percentages.
  - **Extensibility:** Enables future Milestone Invoicing, Stripe billing line items, and Change Orders to cleanly reference specific deliverable IDs.

---

## 3. Decision

We decide to adopt **Option B: Normalize Deliverables into a Dedicated `project_deliverables` Table**.

Upon project conversion (`POST /api/v1/workspaces/:workspaceId/ai/scope/:scopeId/convert`), the deliverables inside `scope_analyses.result.deliverables[]` are materialized as individual rows in `project_deliverables`, referencing `sourceScopeId: scope.id`.

The confirmed scope remains immutable. Project execution mutations (status changes, logged hours) occur strictly on `project_deliverables`.

---

## 4. Schema Specification

```sql
CREATE TYPE "project_deliverable_status" AS ENUM ('pending', 'in_progress', 'completed');

CREATE TABLE "project_deliverables" (
    "id" uuid PRIMARY KEY DEFAULT gen_random_uuid() NOT NULL,
    "workspace_id" uuid NOT NULL,
    "project_id" uuid NOT NULL,
    "title" varchar(255) NOT NULL,
    "description" text,
    "estimated_hours" numeric(6, 2) DEFAULT '0.00' NOT NULL,
    "logged_hours" numeric(6, 2) DEFAULT '0.00' NOT NULL,
    "complexity" varchar(20) DEFAULT 'medium' NOT NULL,
    "status" "project_deliverable_status" DEFAULT 'pending' NOT NULL,
    "position" integer DEFAULT 0 NOT NULL,
    "source_scope_id" uuid,
    "invoice_id" uuid,
    "billed_at" timestamp with time zone,
    "completed_at" timestamp with time zone,
    "created_at" timestamp with time zone DEFAULT now() NOT NULL,
    "updated_at" timestamp with time zone DEFAULT now() NOT NULL,

    CONSTRAINT "fk_project_deliverables_workspace"
        FOREIGN KEY ("workspace_id") REFERENCES "workspaces"("id") ON DELETE CASCADE,
    CONSTRAINT "fk_project_deliverables_workspace_project"
        FOREIGN KEY ("workspace_id", "project_id") REFERENCES "projects"("workspace_id", "id") ON DELETE CASCADE,
    CONSTRAINT "fk_project_deliverables_source_scope"
        FOREIGN KEY ("source_scope_id") REFERENCES "scope_analyses"("id") ON DELETE SET NULL,
    CONSTRAINT "fk_project_deliverables_invoice"
        FOREIGN KEY ("invoice_id") REFERENCES "invoices"("id") ON DELETE SET NULL
);

CREATE INDEX "idx_project_deliverables_workspace_id" ON "project_deliverables" ("workspace_id");
CREATE INDEX "idx_project_deliverables_project_id" ON "project_deliverables" ("project_id");
CREATE INDEX "idx_project_deliverables_status" ON "project_deliverables" ("status");
CREATE INDEX "idx_project_deliverables_invoice_id" ON "project_deliverables" ("invoice_id");
```

---

## 5. Backward Compatibility & Backfill Strategy

For projects created prior to Sprint 17 that do not have rows in `project_deliverables`:
- **Zero Mutation on GET:** Ordinary GET endpoints remain read-only.
- **Explicit Backfill CLI & Endpoint:** An idempotent administrative CLI script (`pnpm --filter @repo/database run backfill:deliverables`) and an explicit POST endpoint (`POST /projects/:projectId/deliverables/backfill`) are provided to unpack legacy scopes safely.
